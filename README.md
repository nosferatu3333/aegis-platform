# AEGIS Platform

AEGIS Platform is a prototype cognitive request service and product-facing
control plane. The current backend MVP accepts a mission, performs deterministic
intent analysis, identifies required capabilities, selects a registered agent
profile through the real registry and matcher, and returns a structured proposed
workflow.

The repository is not an autonomous task executor. Agent selection and workflow
generation are functional, and workflow steps can now pass through a governed,
deterministic simulation that produces an auditable execution receipt.

## Current MVP capabilities

- A real in-process request path from task input to structured result.
- Deterministic intent, complexity, and risk classification.
- Capability-driven profile selection through `AgentRegistry`,
  `CapabilityMatcher`, and `AgentSelectorAdapter`.
- Research and analysis demonstration profiles.
- Explicit failed results when no registered profile matches.
- Stable response schema version `1.0`.
- Per-request correlation IDs accepted or generated by the API.
- Structured decision-path logging using Python's standard `logging` module.
- FastAPI endpoints for task analysis and service health.
- A simulated execution endpoint with explicit request, step, and receipt
  contracts.
- A responsive dashboard served by the same application.
- Authority-gated bounded execution that produces explicit allow, pause, or deny decisions before any execution request is created.
- An end-to-end governed runtime that composes canonical selection, bounded planning, authority gating, simulated execution, conformance, evidence, result, and trace reconciliation.
- Interactive OpenAPI documentation generated by FastAPI.

## Current limitations

- Workflow execution only produces deterministic simulated outputs.
- Research and analysis profiles represent selection capabilities, not external
  tools or independent agents.
- Intent analysis is rule-based and supports a limited vocabulary.
- Confidence and score values are placeholders when the selected profile does
  not provide them.
- There is no authentication, user account, session, database, task history,
  background processing, or production deployment configuration.
- The legacy cognitive orchestrator remains a separate simulated compatibility
  path and is not called by the MVP HTTP pipeline.
- Platform remains a prototype boundary; canonical cognitive authority is
  expected to live outside this product layer.

## Architecture

```text
Browser or API client
        |
        v
FastAPI  GET /  |  GET /health  |  POST /analyze-task | POST /execute-task
                                      |
                                      v
                              IntentAnalyzer
                                      |
                              required capabilities
                                      |
                                      v
AgentSelectorAdapter -> AgentRegistry -> CapabilityMatcher -> AgentProfile
                                      |
                                      v
                              WorkflowGenerator
                                      |
                                      v
                 CognitiveRequestResult schema 1.0
                                      |
                                      v
                    JSON API response / dashboard
                                      |
                                      v
                            ExecutionRequest
                                      |
                                      v
                       Simulated ExecutionEngine
                                      |
                                      v
                      ExecutionReceipt schema 1.0
                                      |
                                      v
                  Conformance + Evidence Reconciliation
                                      |
                                      v
                     ResultRecord + CognitiveTrace
```

The route layer composes and calls the pipeline. It does not implement intent
analysis, matching, selection, or workflow generation.

The concise execution architecture is:

```text
Mission
-> Analysis Pipeline
-> ExecutionRequest
-> Simulated ExecutionEngine
-> ExecutionReceipt
```

`ExecutionRequest` reuses the selected agent, required capabilities, and
generated workflow from `CognitiveRequestResult`; it does not repeat analysis
or planning.

## API

### Analyze a task

`POST /analyze-task`

```powershell
$headers = @{
    "Content-Type" = "application/json"
    "X-Request-ID" = "demo-research-001"
}
$body = @{
    task = "Research competitors in the cognitive systems market"
} | ConvertTo-Json

Invoke-RestMethod `
    -Method Post `
    -Uri "http://127.0.0.1:8000/analyze-task" `
    -Headers $headers `
    -Body $body
```

A successful response contains:

```json
{
  "schema_version": "1.0",
  "request_id": "demo-research-001",
  "task": "Research competitors in the cognitive systems market",
  "intent": {
    "primary_intent": "research",
    "required_capabilities": ["research"]
  },
  "capability": {
    "capability_id": "Research Agent",
    "name": "Research Agent"
  },
  "workflow": [
    {
      "order": 1,
      "title": "Clarify the objective",
      "status": "pending"
    }
  ],
  "status": "ready"
}
```

The actual response includes the complete intent, capability, workflow, and
metadata fields. The `X-Request-ID` header may be supplied by the caller. A UUID
is generated when the header is absent or unsuitable. The identifier is
returned in both the JSON body and response header.

When no profile matches, the endpoint still returns a structured analysis with
`status: "failed"`, an empty workflow, capability ID `unknown`, and
`metadata.failure_code: "no_capability_match"`. Invalid request bodies return
HTTP `422`.

### Simulate execution

`POST /execute-task`

```powershell
Invoke-RestMethod `
    -Method Post `
    -Uri "http://127.0.0.1:8000/execute-task" `
    -ContentType "application/json" `
    -Body '{"task":"Research competitors in the cognitive operating systems market"}'
```

The response contains `analysis`, `execution`, and a top-level
`simulated: true`. The execution receipt uses schema version `1.0`, processes
steps strictly in workflow order, and includes timestamps, counts, step
outputs, and lifecycle audit logs.

**Simulation warning:** no external actions occur. The engine does not access
the internet, call external APIs or tools, run shell commands, modify files, or
persist data.

Request states are `pending`, `ready`, `running`, `waiting`, `completed`,
`failed`, and `cancelled`. This slice follows
`pending -> ready -> running -> completed` on success. Step states are
`pending`, `running`, `completed`, `failed`, and `skipped`. The reserved
`[simulate-failure]` workflow-description marker provides the sole controlled
test failure: that step fails, later steps are skipped, and the receipt ends in
`failed`.

## Benchmark suite

AEGIS Benchmark Suite v0.1 measures deterministic lifecycle consistency using
external JSON missions. It reuses the real analysis pipeline, execution adapter,
and simulated execution engine, then produces JSON and Markdown reports.
Omitted expectations are not scored, and no LLM grading, semantic similarity,
internet access, or real tool execution is used.

```powershell
.\env\Scripts\python.exe -m aegis_benchmark.cli --path benchmarks/missions
```

Default reports are written to `benchmarks/reports/latest.json` and
`benchmarks/reports/latest.md`. See
[`docs/benchmarks/README.md`](docs/benchmarks/README.md) for filters, case
format, scoring, and limitations.

## Prototype boundary

AEGIS currently analyzes missions and simulates their workflow transitions. It
does not perform real workflow actions, call external research systems, mutate
resources, or make autonomous operational decisions. The simulation is
synchronous, single-agent, in-memory, has no retries or approvals, and does not
store receipts. `waiting` and `cancelled` are stable contract states but are not
entered by this first path. Real execution still requires governed tool
adapters, policy and approval enforcement, isolation, measurable results, and
durable audit storage.

See `docs/AEGIS_CURRENT_STATE_DIAGNOSTIC.md` for the detailed repository audit
and `docs/stabilization-phase-2-5.md` for the legacy stabilization boundary.

## External MVP release candidate

AEGIS Platform 1.7.0 can assemble the complete external demonstration evidence set in one command:

```powershell
python scripts/build_release_candidate.py --output-dir ".\release-candidate" --private-key "C:\secure\aegis-release-private.pem" --public-key "C:\secure\aegis-release-public.pem"
```

The output includes the reproducible distribution, detached Ed25519 attestation and signature, public key, trust policy, transparency ledger, trust report, governed acceptance report, and a manifest binding the artifacts to the source commit and tree. The private key is never copied into the release directory. Execution remains deterministic simulation only.
