# v0.5 Phase A — Operational Resource Foundation specification

- **Status:** Draft implementation specification
- **Target:** proposed v0.5.0 Phase A
- **Architecture authority:** [Operational Resource Model](../architecture/operational-resource-model.md)
- **Decision authority:** [ADR-005](../adr/ADR-005-operational-resource-model.md)
- **Depends on:** v0.4.0 contracts and benchmark harness
- **Leads to:** v0.5 Phase B, [Environment Interaction Layer — Simulation First](../architecture/environment-interface.md)

## 1. Purpose

Phase A establishes provider-neutral resource contracts, an in-memory
deterministic catalog, requirement matching, and auditable resolution results.
It gives missions and future workflows a stable way to express:

> I require resource X, with capability Y, under permission Z and constraints C.

Phase A does not access or modify any resource. It does not resolve
environments/adapters, perform discovery, invoke operations, enforce a complete
policy engine, or persist catalog state.

The keywords **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are normative.

## 2. Success boundary

Phase A is complete when code can:

1. construct and serialize valid provider-neutral resource contracts;
2. reject malformed identities, references, descriptors, requirements, and
   relations with stable validation errors;
3. register explicitly supplied synthetic descriptors in an in-memory catalog;
4. resolve a requirement deterministically against catalog entries;
5. distinguish resolved, unresolved, ambiguous, denied, unavailable, and
   unsupported outcomes;
6. preserve reasons, correlations, candidate order, and provenance;
7. prove through tests and benchmarks that no provider, filesystem, network,
   adapter, or external action is involved.

Phase A completion does not mean the resource is accessible or that its
capabilities can be executed.

## 3. Non-goals and exclusions

Phase A MUST NOT introduce:

- filesystem scanning, file reads/writes, or resource mutation;
- network, HTTP, service, provider, or process access;
- environment/adaptor invocation or provider SDKs;
- automatic service/resource discovery;
- persistent storage, databases, caches, or background synchronization;
- semantic/vector search or adaptive ranking;
- a knowledge graph;
- memory or knowledge integration;
- credential/secret storage or resolution;
- policy/approval UI or a complete authorization engine;
- autonomous resource acquisition;
- changes to `/analyze-task`, `/execute-task`, execution transitions, or
  dashboard behavior;
- new runtime dependencies.

All catalog data used in Phase A MUST be explicitly constructed in memory by a
caller, test, benchmark, or future composition layer.

## 4. Proposed package boundary

Implementation is expected to use one focused package:

```text
aegis_os/resources/
    __init__.py
    models.py
    errors.py
    catalog.py
    resolver.py
```

This layout is a specification recommendation, not code created by this task.

- `models.py` owns immutable/factory-safe contracts and enums.
- `errors.py` owns stable validation/catalog error codes and exceptions.
- `catalog.py` owns deterministic in-memory registration and lookup.
- `resolver.py` owns requirement evaluation and resolution output.
- `__init__.py` exports only the stable Phase A public surface.

The package MUST NOT import FastAPI, execution engine, environment adapters,
legacy memory/knowledge modules, filesystem/network libraries, or provider
packages. Existing pipeline, execution, and benchmark code MUST remain
behaviorally unchanged during Phase A unless a later implementation task
explicitly authorizes narrow additive integration.

## 5. Schema and identifier conventions

Phase A resource contracts use schema version `"1.0"`.

Identifiers MUST:

- be non-empty strings;
- contain only ASCII letters, digits, `.`, `_`, `-`, and `:`;
- be at most 128 characters;
- be case-sensitive after validation;
- remain opaque to consumers;
- never be inferred by parsing a provider URI/path.

Suggested identifier forms:

```text
namespace: workspace:demo
resource_id: resource:benchmark-suite
type_id: type:dataset
capability_id: capability:read
requirement_id: requirement:benchmark-input
resolution_id: resolution:benchmark-input:001
```

The implementation MUST NOT generate random IDs inside resolution logic.
Callers SHOULD supply IDs, or a deterministic injected ID factory MAY be used.

## 7. Contract specifications

Contracts SHOULD be dataclasses consistent with current repository style.
Defaults MUST use immutable values or factories. Serialization MUST return
JSON-compatible dictionaries and enum values as strings.

### 7.1 ResourceType

| Field | Type | Required | Rules |
|---|---|---:|---|
| `type_id` | string | yes | valid stable identifier |
| `name` | string | yes | non-blank display name |
| `category` | `ResourceCategory` | yes | top-level classification |
| `description` | string | yes | non-blank |
| `capability_ids` | tuple/list of string | no | unique, stable order |
| `parent_type_id` | string/null | no | cannot equal `type_id` |
| `schema_version` | string | yes | default `"1.0"` |

Invariants:

- A type MUST remain provider-neutral.

## 8. Stable error taxonomy

Validation/catalog API failures use stable categories:

- `invalid_identifier`
- `invalid_type`
- `invalid_reference`
- `invalid_descriptor`
- `invalid_requirement`
- `invalid_constraint`
- `invalid_relation`
- `duplicate_resource`
- `resource_not_found`
- `type_not_found`
- `catalog_conflict`
- `secret_value_prohibited`
- `unsupported_schema_version`

Resolution outcomes are not raised as exceptions. `unresolved`, `ambiguous`,
`denied`, `unavailable`, and `unsupported` MUST return a
`ResourceResolution`.

Exceptions MUST expose a stable code and safe message. They MUST NOT include
full descriptors, locators, metadata, provenance payloads, or secret-like
values.

## 9. In-memory deterministic catalog

### Public behavior

The catalog SHOULD expose:

- `register_type(resource_type)`
- `get_type(type_id)`
- `list_types()`
- `register(descriptor)`
- `get(reference)`
- `list_descriptors()`
- `remove(reference)` only as in-memory catalog administration, not resource
  deletion
- `resolve(requirement, resolution_id)`

`remove` MAY be omitted from initial implementation. If present, it removes
only the catalog record and MUST NOT change the described resource.

### Ordering

- Types MUST list in ascending `type_id`.
- Descriptors MUST list by `(namespace, resource_id)`.
- Locations, capabilities, permissions, labels, and relations MUST serialize in
  canonical stable order.
- Candidate evaluation MUST use catalog order.
- No result may depend on Python hash/dictionary insertion accidents.

### Registration

- Duplicate `(namespace, resource_id)` registration MUST fail with
  `duplicate_resource`.
- Replacement/update semantics are excluded. A future explicit `replace` API
  requires version/concurrency policy.
- Catalog registration MUST validate descriptor structure but MUST NOT check a
  provider or location.
- Catalog construction MUST have no global singleton or import-time mutation.

### Lookup

`get(reference)` MUST:

1. validate the reference;
2. find the exact identity;
3. apply exact version/revision selectors;
4. return a descriptor or stable `resource_not_found`;
5. never dereference a location.

## 10. Requirement matching

A candidate satisfies required matching only when:

1. its `type_id` appears in `requirement.type_ids`;
2. every required capability is declared by the descriptor;
3. every required permission is declared by the descriptor;
4. every required constraint evaluates true;
5. exact version/revision selectors match when supplied;
6. lifecycle/state rules permit selection;
7. freshness and trust requirements match.

Capabilities and permissions use set inclusion for eligibility, but serialized
order remains canonical.

Preferred constraints and `preferred_environment_id` affect rank only after all
required checks pass. They MUST NOT make an ineligible candidate eligible.

## 11. State and authority filtering

Phase A has no policy engine. It still needs deterministic outcome semantics:

| Descriptor condition | Candidate outcome |
|---|---|
| `available` | eligible if other checks pass |
| `declared` | eligible only when no freshness/availability requirement is implied; Phase A SHOULD treat as available for synthetic tests and record `state_declared` |
| `stale` | rejected when freshness required; otherwise eligible with reason |
| `unavailable` | reject as unavailable |
| `restricted` | reject as denied |
| `archived` | reject unless a required constraint explicitly permits archived resources; no such constraint is in the initial allowlist, so reject |
| `deleted` | reject as unavailable |
| `invalid` | reject as unsupported/invalid |

Tenant, owner, and authority constraints are exact. Absence MUST NOT satisfy a
required equality constraint.

Declared permissions represent catalog metadata only; they are not policy
grants. A matching Phase A result means “the descriptor claims compatibility,”
not “the caller is authorized to act.”

## 12. Resolution algorithm

For identical inputs, the algorithm MUST be deterministic:

1. Validate the requirement.
2. If a required constraint kind is unsupported, return `unsupported`.
3. List descriptors in canonical catalog order.
4. Produce one `CandidateEvaluation` per descriptor.
5. Filter candidates using required type, capability, permission, constraint,
   selector, state, freshness, trust, owner, authority, and tenant rules.
6. Classify rejection reasons.
7. Rank eligible candidates by:
   1. number of matched preferred constraints, descending;
   2. preferred-environment match (`1` before `0`);
   3. `(namespace, resource_id)`, ascending.
8. Apply cardinality and ambiguity rules.
9. Return a `ResourceResolution`; do not invoke anything.

### Ambiguity

For `one` and `zero_or_one`, if the highest two candidates have identical
preference scores before the deterministic identity tie-breaker, the outcome
MUST be `ambiguous`, not an arbitrary selection. Identity ordering is for stable
audit output, not permission to hide semantic ambiguity.

For `one_or_more` and `zero_or_more`, all eligible candidates MAY be selected
in rank order.

### Empty results

| Cardinality/optional | No eligible candidate |
|---|---|
| `one` | `unresolved`, unless all plausible candidates are denied/unavailable/unsupported |
| `zero_or_one` | `resolved` with empty selection |
| `one_or_more` | `unresolved` |
| `zero_or_more` | `resolved` with empty selection |
| any `optional=True` | MAY return `resolved` empty, but reason MUST record `optional_unresolved` |

Status precedence when no candidate is eligible:

1. `denied` if at least one type/capability-compatible candidate was restricted
   or failed an authority/tenant permission constraint;
2. `unavailable` if at least one otherwise-compatible candidate was unavailable,
   deleted, archived, or stale under freshness;
3. `unsupported` if type/capability/required constraint semantics are
   unsupported;
4. `unresolved` otherwise.

## 13. Serialization and immutability

- All public contracts MUST support deterministic `to_dict()`.
- Enum fields serialize to their string values.
- Tuples/lists serialize as JSON arrays in canonical order.
- Datetimes, if present, serialize as timezone-aware ISO 8601.
- Mappings MUST be copied on input or serialization to prevent shared mutation.
- Unknown arbitrary Python objects MUST be rejected.
- Secrets and credential values MUST be rejected or excluded; only opaque
  reference identifiers are allowed.
- Round-tripping through `json.dumps`/`json.loads` MUST succeed.

Contracts SHOULD be frozen where practical. If mutable dataclasses are used for
repository consistency, tests MUST prove safe defaults and serialization
isolation.

## 14. Secret-exclusion rules

Phase A cannot reliably classify every secret. It MUST nevertheless:

- prohibit fields named `password`, `secret`, `token`, `api_key`,
  `access_key`, `private_key`, or `credential_value` in metadata/provenance;
- allow only opaque `credential_reference` identifiers;
- reject nested prohibited keys recursively;
- avoid echoing rejected values in errors/logs;
- treat locators as potentially sensitive and omit them from resolution audit
  summaries.

This validation is a defense-in-depth baseline, not a secret-management system.

## 15. Integration boundaries

### Cognitive pipeline

No Phase A change is required to `CognitiveRequestResult`. A later additive
integration may introduce resource requirements in a new schema/version.
Resource inference is not part of initial runtime delivery unless separately
specified and benchmarked.

### Workflow and execution

No Phase A change is required to `WorkflowStep`, `ExecutionRequest`,
`ExecutionStep`, or `ExecutionReceipt`. Phase A MUST NOT alter execution state
transitions. Later work may carry `ResourceReference`/`resolution_id` values in
versioned fields.

### Environment Interaction Layer

Phase B environment requests SHOULD target Phase A resolved references where an
operation has a semantic resource target. Phase A MUST NOT import Phase B.

### Governance

Phase A matching of declared permissions is compatibility filtering, not
authorization. The future governance layer remains authoritative.

### Memory and knowledge

No integration. Catalog records are not memory, observations, or verified
knowledge.

### API and dashboard

No endpoints, request fields, response fields, or UI changes.

## 16. Logging and observability

Phase A implementation SHOULD use standard Python logging for catalog
registration and resolution summary only:

- resource/reference IDs;
- requirement/resolution IDs;
- candidate/selected counts;
- terminal resolution status;
- stable error/reason codes.

It MUST NOT log full metadata, provenance, locator values, or request payloads.
Logging MUST NOT be necessary for deterministic result correctness.

## 17. Test specification

Create a focused `tests/resources/` suite when implementation is authorized.
Minimum coverage:

### Models

- valid construction and serialization for every contract;
- safe mutable defaults/input copying;
- enum serialization;
- invalid/blank/oversized identifiers;
- duplicate nested IDs;
- invalid timestamps/version ranges;
- reference contains no descriptor/location payload;
- recursive secret-key exclusion;
- JSON round trip.

### Catalog

- type and descriptor registration;
- canonical list ordering;
- duplicate registration;
- exact reference lookup;
- version/revision selector match and mismatch;
- catalog instance isolation;
- no import-time/global state;
- removal, if implemented, does not imply external deletion.

### Resolver

- exact type, capability, and permission matching;
- required versus preferred constraints;
- preferred environment ranking;
- resolved single and multiple cardinalities;
- unresolved, ambiguous, denied, unavailable, unsupported;
- optional empty behavior;
- stale/freshness and lifecycle filtering;
- owner/authority/tenant mismatch;
- immutable/readonly resource compatibility;
- stable candidate reason codes;
- identical inputs produce identical serialized resolution;
- no filesystem/network/provider invocation.

### Relations/provenance

- valid directional relation;
- prohibited self-relation;
- no transitive permission inference;
- source correlation;
- provenance copying and secret exclusion.

## 20. Implementation sequencing

An authorized implementation SHOULD proceed in reviewable increments:

1. enums, identifier validation, errors, and basic models;
2. descriptor/reference/location/state validation and serialization;
3. in-memory catalog and deterministic lookup;
4. requirement/constraint/candidate/resolution contracts;
5. deterministic resolver and reason taxonomy;
6. focused tests and full regression suite;
7. optional benchmark model/fixture extensions;
8. documentation conformance review.

No increment may introduce external discovery or action.

## 21. Acceptance criteria

Phase A implementation is acceptable only when:

- the public resource package is typed, serializable, and provider-neutral;
- catalog behavior is deterministic and entirely in memory;
- resolution implements the status/ranking/cardinality rules in this
  specification;
- ambiguity is explicit rather than hidden by tie-breaking;
- stable errors and candidate reason codes are tested;
- references contain no payloads, locations, or credentials;
- secrets are excluded from metadata/provenance and safe errors;
- the kernel/pipeline/execution engine import no provider implementation;
- there is no filesystem, network, process, adapter, or persistence behavior;
- existing API/execution behavior is unchanged;
- focused resource tests, full tests, and benchmarks pass;
- documentation and ADR-005 remain accurate.

## 22. Deferred decisions

The following require separate decisions or specifications:

- authoritative namespace allocation and cross-tenant identity;
- type-registry ownership and extension review;
- descriptor replacement/concurrency/version migration;
- ordered trust taxonomy;
- policy-granted permissions versus descriptor claims;
- persistent catalog technology and query model;
- provider/location verification;
- cryptographic provenance and audit retention;
- observation contracts and promotion into memory/knowledge;
- adaptive/semantic discovery and ranking;
- workflow/API schema integration;
- execution-to-interaction receipt references.

Phase A MUST choose conservative deterministic behavior or fail closed where
these decisions would otherwise affect authorization or external action.
