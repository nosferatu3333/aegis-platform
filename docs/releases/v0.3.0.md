# v0.3.0 — Governed execution

## Release identity

- **Tag:** `v0.3.0-governed-execution`
- **Commit:** `27094b9e1096fdb8798981fb0032424cbc174a22`
- **Date:** 2026-07-26
- **Status:** Completed historical milestone

## Objective

Establish stable execution contracts and auditable state transitions before
introducing any real tool action.

## Delivered

- `ExecutionRequest`, `ExecutionStep`, and `ExecutionReceipt`.
- Request and step status enums and schema version `1.0`.
- Adapter from ready `CognitiveRequestResult`.
- Ordered simulated engine with deterministic output and timestamps.
- Reserved `[simulate-failure]` behavior and skipped subsequent steps.
- `POST /execute-task`, dashboard execution display, correlation IDs, and
  standard logging.
- Focused execution and API regression tests.

## Architecture impact

The release created the separate layer documented in the
[execution engine](../architecture/execution-engine.md). Analysis remained
unchanged and reusable; execution consumed its result rather than duplicating
classification or workflow generation.

## Verification

The tagged tree contains execution model, adapter, success, lifecycle,
determinism, malformed-request, controlled-failure, API, and dashboard tests.
Git does not store a numeric test run for this tag.

## Known limitations

All execution was simulated. Permissions and constraints were descriptive;
there was no governance policy engine, approval flow, tool isolation, retry,
queue, persistence, or multi-agent execution.
